# 三、为什么我要把 Control Plane 单独提出来

你最大的诉求一直不是“Agent 更聪明”，而是：

> 以后加“膏方”“时值冬令”“以膏代煎”“儿科”“新专科”，我自己在管理后台改，不要每次找开发改 Python/TypeScript。

这个目标能实现。

但**绝不能让管理员保存一条 YAML，下一位患者立即生效**。

否则只是从：

```text
代码里的 if/else
```

变成：

```text
数据库里的 if/else
```

甚至风险更大。

所以管理员实际上操作的是：

```text
DRAFT CONFIG
     ↓
Schema Validation
     ↓
Dependency / Compatibility Check
     ↓
Policy Static Analysis
     ↓
Golden Eval
     ↓
Invariant / Safety Test
     ↓
SHADOW
     ↓
CANARY
     ↓
ACTIVE
```

之前讨论中形成的发布流程是正确的，我建议直接保留为平台铁律。

但现在再多一步：

```text
ACTIVE
   ↓
Runtime Release Compiler
   ↓
EffectiveRuntimeRelease@hash
```

Runtime **只读取已经编译完成的不可变 Release**。

不读取后台正在编辑的 Skill。

不读取管理员正在修改的 Prompt。

不读取半成品 Policy。

这一步非常重要。

Platform Safety → Pack Policy → Tenant Policy，只能越来越严格。

# 八、HITL 我建议正式拆成三类


# 九、方剂权威机制继续保留三层，不建议再动

```text
FinalClinicalStrategy
       ↓
Formula Resolver
   ┌──────┴───────┐
   ↓              ↓
NORMATIVE   GENERATED_DRAFT
   └──────┬───────┘
          ↓
   Formula Validator
          ↓
   Doctor Clinical HITL
          ↓
        COMMIT
```

语义仍然是：

**NORMATIVE**：知识库存在明确权威源方，直接绑定 `formula_id/source_id/composition/provenance`，LLM 不重新抄写。

**GENERATED_DRAFT**：安全通过、临床目标明确，但无直接规范方或存在合理不确定性，可以产生医生审核稿。

**BLOCKED**：身份、安全、完整性、方药验证或系统完整性真正失败。

一定不要恢复：

```text
selected_syndrome == null
→ BLOCKED
```

这一旧逻辑。

# 十、你现在这个知识库，怎么迁移最合理

我实际检查后，不建议“把整个 PGYxv1.0 做向量化然后全部 RAG”。

它应该进入一个正式的 **Knowledge Registry + Knowledge Release Compiler**。

而且你现在的资产天然就已经能分层：

| 当前资产                        | 新系统中的位置                                |
| --------------------------- | -------------------------------------- |
| 原始专著、国标、文档                  | `source / immutable provenance`        |
| V2 `2026.09.4-kb-parity-r1` | Runtime candidate，保留它原有 fail-closed 状态 |
| V3.5 clinical policy        | `SHADOW`，绝不自动提升运行时权威                   |
| regression / holdout / gold | `EVALUATION_ONLY`                      |
| medication safety           | Safety asset，由 Clinical Core 消费        |
| legacy `pgy.db`             | 一次性迁移源，不是 Runtime DB                   |

我实际跑了资产检查以后还有一个很有价值的发现：

**知识内容本身并没有丢。**

之前出现大量 `#U4e2d...` 文件名，是 ZIP 的中文文件名跨平台编码导致的。用能够正确读取 Unicode extra field 的方式解包后，原校验器可以通过：

```text
274 retained assets
128,706,762 bytes
```

所以 M0 不应该去“修知识内容”。

应该修的是：

```text
资产打包规范
+
UTF-8 文件名
+
manifest canonical path
+
checksum verification
```

此外，V3.5 自己已经明确是：

```text
SHADOW_SOURCE_RECOMPILED_FINAL_NOT_RUNTIME_AUTHORITY
```

这个状态新 Runtime 必须尊重。

不能因为它“更新”，就自动覆盖 V2 的运行权威。

# 十二、技术栈现在可以正式锁死

截至 **2026 年 9 月 16 日**，Vercel AI SDK 7 已经原生提供 `ToolLoopAgent`、typed tool/runtime context、tool approval、durable `WorkflowAgent`、timeouts、telemetry 等能力，因此我们的确没有必要自己重新制造 Agent Loop、流式协议和 durable approval 框架。([Vercel][1])

所以我建议：

| 层                       | 最终选择                                       |
| ----------------------- | ------------------------------------------ |
| Web                     | Next.js + React + TypeScript               |
| Clinical Agent Platform | TypeScript                                 |
| Agent Runtime           | AI SDK 7 Adapter                           |
| Durable workflow        | WorkflowAgent / WorkflowPort               |
| Clinical Core           | Python 3.12+ + FastAPI                     |
| Contracts               | JSON Schema / OpenAPI 3.1                  |
| TS models               | 自动生成 TypeScript/Zod                        |
| Python models           | 自动生成 Pydantic                              |
| Database                | PostgreSQL                                 |
| Vector                  | pgvector 第一阶段足够                            |
| Retrieval               | lexical + dense + rerank + source fallback |
| Internal protocol       | Typed HTTP / OpenAPI                       |
| External integration    | MCP                                        |
| Trace                   | OpenTelemetry                              |
| Deployment V1           | Docker Compose                             |

前面的“Schema 是唯一 Source of Truth，不允许 Pydantic 和 Zod 两边手写”必须严格执行。

MCP 继续只用在外部边界。截至现在 TypeScript SDK v2 已是稳定线并覆盖新的 MCP 规范；实现时建议显式配置版本协商，而不是依赖默认行为。([MCP TypeScript SDK][2])

# 十四、开发完整路径

我建议严格按下面 10 个阶段推进，不要一开始就接模型然后看起来“会聊天”。

1. **M0：资产与安全防火墙。** 重新规范知识包打包；解决中文 ZIP 路径；以现有 SHA-256 Manifest 为基准做 `asset verify`；把 `_private/legacy.env` 从任何发行包、Docker context、Git 工件里彻底排除，并轮换其中历史凭据。把 V2、V3.5、evaluation 的 Authority 状态转换成新的 `KnowledgeRegistry`，但绝不改变原始状态。M0 的完成标准不是“服务能启动”，而是**任何知识资产无法说明来源、authority、runtime_allowed、checksum 时禁止发布**。

2. **M1：Contracts + Monorepo 地基。** 先定义 `PatientIdentity`、`Encounter`、`FactCandidate`、`Fact`、`Evidence`、`Hypothesis`、`ClinicalProblem`、`Objective`、`Strategy`、`FormulaProposal`、`SafetyDecision`、`DoctorDecision`、`PlatformEvent`、`EffectiveRuntimeRelease`。由 JSON Schema/OpenAPI 自动生成 TS/Python 类型；CI 检查生成物 drift。这个阶段不接 LLM。

3. **M2：Clinical Authority Kernel。** 先完成 tenant/doctor/patient/encounter 隔离、Fact authority、Safety authority、Doctor Decision、Formula Authority、Audit。实现 `MATCH / AMBIGUOUS / NEW / INSUFFICIENT` 身份解析状态，以及 `NORMATIVE / GENERATED_DRAFT / BLOCKED`。这是整个系统最应该测试最多的地方。

4. **M3：State + Legacy Migration。** 建 PostgreSQL 新模型；使用“当前状态表 + append-only authority event”的方式，不做教条式全事件溯源。写一次性 `pgy.db` 迁移器，迁移 clinic/user/patient/thread/encounter/message 等历史实体；旧 AI 结论不能因为存在数据库里就自动升级成 authoritative fact。

5. **M4：Knowledge Platform。** 建 Source Registry、Knowledge Release、chunk/provenance、lexical/dense/rerank。先把 V2 作为受其原 manifest 状态约束的 runtime candidate；V3.5 只进入 shadow；evaluation 数据所在的存储路径和服务凭据与 runtime 物理隔离。完成 `knowledge.search`、`knowledge.get_source`、`formula.search_normative` 等高内聚工具。

6. **M5：Clinical Agent Platform 最小闭环。** 建 `AgentRuntimePort`、`ToolPort`、`ModelPort`、`ApprovalPort`，然后实现 AI SDK 7 Adapter。第一版只有一个 Clinical Primary Agent；先实现 `context snapshot → fact candidates → safety → evidence → problem/objective → strategy → formula proposal → doctor decision`。所有 AI 输出都只是 Proposal，不能直接写 Clinical State。

7. **M6：Capability / Skill / Policy / Inquiry。** 实现 Capability Registry、受限 Policy DSL、Capability Resolver、Skill JIT activation、Inquiry Matrix。候选 Capability 控制在 2～3 个以内，不允许把几十个 Skill 全塞给模型；Workflow 只支持稳定 primitive，例如 Resolve Identity、Acquire Facts、Evaluate Safety、Resolve Capability、Retrieve、Reason、Validate、Approval、Commit，不做自由 `IF/ELSE/JUMP` 可视化编程器。这个原则在之前的讨论里已经明确。

8. **M7：UI 1:1 迁移。** 按现有 UI shell 重建 Next.js 页面；医生工作台和管理员后台先共用一个应用。聊天流改成 PlatformEvent；前端只呈现 Clinical View Model，不判断安全、不推导权威、不持久化 clinical state。原来的机构、账号、API Key、日志、质控继续保留，同时增加 Agent Studio、Capability Center、Skill、Policy、Tool、MCP、Knowledge、Inquiry、Eval、Trace、Release。

9. **M8：Release Compiler + Eval Center。** 管理员修改任何 Prompt、Pack、Policy、Knowledge、Model Profile 后只形成 DRAFT；通过 Schema、dependency、compatibility、Golden、Invariant 后进入 Shadow/Canary；最后编译为不可变 `EffectiveRuntimeRelease`。每个 ClinicalRun 固定 release hash，运行过程中绝不因管理员发布新版本而漂移。

10. **M9/M10：集成与生产化。** 最后再接 HIS/LIS/PACS/MCP、语音、外部文献和药物数据库。外部 MCP 永远先经过 Tool Gateway → normalize/validate → FactCandidate → Authority Kernel，不能直接写 Encounter。随后补齐 OTel、PHI 日志脱敏、备份恢复、灾难演练、Rate Limit、Secrets Manager、租户审计、Shadow telemetry、Canary rollback，才进入真正生产部署。

# 十六、这次架构重构最重要的验收题，不是“能不能跑一个病例”

真正的架构验收，我建议直接用我们之前设想过的场景：

> 三个月以后，你说：“我要增加一个冬令膏方调补 2.0，胃纳不佳者先调脾胃再进膏。”

开发人员应该只需要：

```text
复制 gaofang Capability Pack
修改 Skill
更新 Inquiry Matrix
导入知识
增加声明式 activation/policy
新增 Golden Cases
跑 Eval
Shadow
Canary
发布
```

而下面这些应该全部：

```text
Clinical Primary Agent 主代码      0 行修改
Authority Kernel                   0 行修改
核心 DB Schema                     0 行修改
Clinical Core 主流程               0 行修改
```

这其实就是我们前面已经形成的最终插件化验收标准。

如果做不到这一点，即使系统用了 AI SDK、MCP、Agent、RAG，也只能说明：

> **我们只是用新的技术重新写了一套旧系统。**

## 最终结论

这次我不建议再重新讨论“LangGraph 还是 CrewAI”“要不要五个 Agent”“病名 Agent 是否先于证型 Agent”这类问题了。

**架构可以正式冻结。**

最终核心应该只有一句话：

> **平台提供稳定边界；Capability Pack 提供可插拔业务能力；Agent 在边界内动态理解、检索与规划；Knowledge 提供证据；Authority Kernel 决定哪些 Proposal 可以成为临床事实和临床动作；Control Plane 决定这些能力如何安全地配置、测试和发布。**

而你现在这三个材料已经足够正式开始工程：**UI 用作视觉和交互基线，PGYxv1.0 用作知识/评测资产基线，历史讨论中这一版平台架构作为 Architecture Baseline。**

下一步最合理的不是继续画架构图，而是直接进入 **M0 + M1：资产防火墙、凭据治理、仓库骨架、Contracts、代码生成和第一批架构不变量测试**。这一步做实以后，后面的 Agent、知识检索和 UI 才不会再次长成旧系统。
