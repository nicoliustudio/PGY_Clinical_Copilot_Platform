## 2. 链路分层总览

```text
【入口层】   前端 ui/app.js ──POST /api/run/stream (SSE)──▶ src/server/http.ts
             scripts/*.ts ──直接调用 runCase──▶ 同一运行时

【组合根】   src/composition/runtime.ts
             createClinicalRuntime(): 资产发现 → 注册表 → 安全端口 → 理解端口 → 装配器 → 提示词 → Authority 链

【运行时外壳】src/platform/agent/clinical-runtime.ts
             prepare → Agent 推理 → canonical hydrate → Authority 校验 → 结果/追踪

【Prepare】  RuntimePreparer
             ① 语义理解（Understanding）  ② 安全处置（Safety）
             ③ 临床总策划（Planner）      ④ 播种临床工作区  ⑤ 建立 Harness 会话

【推理层】   AiSdkPrimaryAgent.run（多步工具循环）
             动态指令 = 系统提示 + 行动原则 + 激活 Skill + Clinical Working View
             工具面 = 能力发现 / 知识检索 / 方剂两阶段检索 / 工作区写入 / 提交
             终止 = Agent 提交 ｜ 状态完备由内核确定性序列化 ｜ 预算耗尽如实标记未完成

【状态层】   ClinicalWorkspace（事件溯源 + 版本号 + 投影缓存）
             病例事实 / 证据 / 假设 / 候选与权衡 / 辨证结构 / 临床决策主干

【知识层】   只读：release 知识（规范病-证-法-方、国标、诊断知识）
                  + Runtime Catalog（膏方/针灸/制剂轻量卡片与详情）

【Authority】SafetyInvariantStage → FormulaAuthorityStage（Agent 不可绕过）
```

## 3. 一次 Run 的函数级链路

```text
前端 send() / 脚本 runCase()
  └─ src/composition/runtime.ts  runCase()
       ├─ getClinicalRuntime(mode)          # 按 mode 缓存的运行时装配
       ├─ newTrace(input)                   # 生成 runId
       └─ ClinicalRuntime.run()
            ├─ 1. RuntimePreparer.prepare()
            │      understand(input) → RiskHypothesisSafetyPort.evaluate() → StructuredClinicalPlanner.plan()
            │      → createClinicalWorkspace()（播种 caseFacts / gaps / safetyDisposition / clinicalQuestion）
            │      → new HarnessSession()
            ├─ 2. AiSdkPrimaryAgent.run()      # 主循环，逐步发射 tool-call / workspace / lifecycle 事件
            ├─ 3. recordCandidateDecision / recordHypothesisDecision
            ├─ 4. hydrateFormulaProposal()     # candidate_ref → canonical 方剂身份（模型不得自造身份）
            ├─ 5. withCanonicalSafety          # 安全结论以内核为准
            ├─ 6. AuthorityPipeline.resolve()
            │      SafetyInvariantStage → FormulaAuthorityStage(DeterministicFormulaAuthority)
            └─ 7. 返回 result / authority / workspace / trace 快照
  └─ buildSessionView() → SSE result → 前端渲染（医生视图 + 管理员 Trace 视图）
```

**提交门禁（唯一的 readiness 口径）**：`src/platform/workspace/proposal-readiness.ts`

- 最小临床主干未成形 → 阻断
- 存在未处置的正式假设 → 阻断
- 收敛已达成却想以「追问」收尾 → 阻断
- 完成义务缺产物（如要求开方但未选定候选方）→ 阻断

**终结语义（区分「完成」与「没做完」）**：

| 状态 | 含义 |
|---|---|
| agent_submitted | Agent 主动提交 |
| runtime_committed_ready_state | 状态已完备，由内核确定性序列化（不再让模型重写结论） |
| execution_incomplete | 预算耗尽且产物不全，**如实标记，不伪装成追问** |

## 4. 核心设计约束（供专家核对是否成立）

| 约束 | 代码落点 |
|---|---|
| 理解一次、处处消费 | `src/clinical/understanding.ts` + `src/contracts/understanding.ts` |
| 总策划只定策略，不下病/证/方结论 | `src/platform/planning/clinical-planner.ts` |
| 能力不预路由，由 Agent 运行时发现并激活 | `src/platform/runtime/harness-session.ts` |
| 检索不得自动升级为患者结论 | `src/contracts/workspace.ts`（hypothesis.origin）、`scripts/check-architecture.ts` |
| 规范方身份由内核 hydrate，模型只提交引用 | `src/platform/agent/clinical-runtime.ts`、`src/clinical/formula-candidate.ts` |
| Authority 只验权限/来源绑定/安全处置 | `src/authority/formula-authority.ts`、`src/platform/authority/*` |
| 安全判定读结构化处置，不读病名关键词 | `src/clinical/risk.ts`、`src/clinical/understanding.ts` |
| 认知方法（Skill）不含病例答案 | `skills/*/SKILL.md` |
| 评测数据不进入运行时知识 | `scripts/check-architecture.ts`、`src/eval/*` |

## 6. 如何运行（复现用）

```bash
# 1) 安装依赖
npm install

# 2) 配置环境变量（复制 .env.example 后填写）
#    必需：KB_RELEASE_DIR, LLM_BASE_URL, LLM_API_KEY, LLM_FAST_MODEL, LLM_DEEP_MODEL,
#          EMBEDDING_*, RERANK_*, APP_SECRET
cp .env.example .env

# 3) 类型检查 / 单元测试 / 架构守卫
npm run typecheck
npm test
npm run arch:test

# 4) 启动服务（默认 8787），前端在 /login 登录
npm run serve

# 5) 跑一次全链路采集（8 例 × 3 次），产物在 reports/
npx tsx scripts/collect-8x3.ts
npx tsx scripts/render-8x3.ts
```

**runtime 双模式**：`CLINICAL_RUNTIME_MODE=harness`（默认，Agent 自主发现能力）或 `classic`（对照基线，A/B 基础设施开关，不是临床分支）。

## 7. 专家可重点提出的质疑点

1. **安全边界**：`src/clinical/risk.ts` 的处置判定是否覆盖了临床真正需要的红线？是否存在「严重但非紧急」被误升为阻断、或紧急被放行的情况？
2. **规范方权威**：`src/authority/formula-authority.ts` 只校验「来源 + 方名 + 组成」三者同源，是否需要叠加剂量、炮制、禁忌层面的校验？
3. **证候与病机表达**：系统刻意不建立中医证型枚举（全部开放文本），这是否会导致辨证术语不收敛、难以审计？
4. **提交门禁**：`proposal-readiness.ts` 的四类阻断码是否与临床实际的工作流一致（例如仅要求辨证时是否会强行索要方剂）？
5. **检索与决策分离**：知识层被约束为只读，是否会损失「以方测证」等传统推理路径的合法性？
6. **加味与制剂**：`modificationPlan` / 治疗形式决策（膏方、外治、制剂）的边界是否清晰，是否存在把个案用药当作规范方提交的风险？
